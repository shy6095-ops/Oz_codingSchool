# AI Health Web Assignment

흉부 X-ray 이미지로 폐렴 여부를 예측하고 환자 정보를 관리하는
FastAPI 기반 웹 서비스입니다. (오즈코딩스쿨 팀 프로젝트)

## 아키텍처

| 서비스 | 역할 |
|--------|------|
| `fastapi` | 환자 관리 / 인증 API. 예측 요청을 Redis 큐에 적재 |
| `ai-worker` | 큐에서 X-ray 추론 작업을 꺼내 PyTorch(CPU)로 폐렴 예측 후 pub/sub 으로 결과 반환. `--scale ai-worker=3` 으로 수평 확장 |
| `mysql` | 환자·예측 데이터 (SQLAlchemy + Alembic) |
| `redis` | 작업 큐 및 결과 전달 |

이미지 용량을 줄이기 위해 웹 계층(`app`)과 AI 워커(`ai`)의 의존성을 분리합니다.

## Alembic Migration Guide

이 프로젝트는 데이터베이스 마이그레이션을 위해 Alembic을 사용합니다.

### 1. 마이그레이션 파일 생성 (자동 생성)
모델(`app/models/`)이 변경된 경우 다음 명령어를 실행하여 마이그레이션 파일을 생성합니다.
```bash
uv run alembic revision --autogenerate -m "변경 내용 설명"
```

### 2. 데이터베이스에 반영
생성된 마이그레이션을 데이터베이스에 적용하려면 다음 명령어를 실행합니다.
```bash
uv run alembic upgrade head
```

### 3. 이전 상태로 되돌리기 (Rollback)
마지막 마이그레이션을 취소하려면 다음 명령어를 실행합니다.
```bash
uv run alembic downgrade -1
```

## 2. 사용자 요구사항 정의

**진행 방식** — 과제로 제공된 요구사항을 읽고, 각 API 설계서에서 `REQ-USER-001`, `NFR-PRED-002` 같은 **ID로 인용하는 방식**으로 진행했습니다. 명세와 코드 주석에 같은 ID를 달아 추적할 수 있게 했습니다.

**문제와 해결** — 프로젝트 막바지에 점검해 보니 **요구사항 ID는 곳곳에서 참조되는데 정의서 자체는 저장소에 없었습니다.** 읽고 넘어갔을 뿐 우리 손으로 쓴 문서가 아니었기 때문입니다.
그래서 흩어진 요구사항을 [요구사항 정의서](docs/요구사항_정의서.md)로 직접 통합했습니다.

- 액터를 정의하며 **권한이 역할(`role`)과 부서(`department`) 두 축으로 갈린다**는 점을 처음으로 명문화했습니다. (관리자 기능은 역할, 등록 기능은 부서로 통제)
- 인수 조건은 문서상의 표현이 아니라 **실제 구현 동작을 확인해 가며** 작성했습니다.
- 배포·운영 요구사항(`REQ-OPS`, `NFR-OPS`)을 팀 자체 항목으로 신설해 8·9단계의 완료 판정 기준을 만들었습니다.
- 그 과정에서 **판단이 필요한 4건**을 발견해 임의로 정하지 않고 미결 사항으로 분리했습니다.
  가입 직후 `PENDING` 회원이 사실상 모든 조회 API를 쓸 수 있는 점, 예측 API의 동기 대기, 환자 수정·삭제에 부서 제한이 없는 점, 회원 탈퇴의 하드 삭제입니다.

**배운 점** — 요구사항을 "읽는 것"과 "쓰는 것"은 다릅니다. 직접 쓰기 시작하자 **구현에는 있는데 아무도 합의한 적 없는 동작**들이 드러났습니다.

## 7. 아키텍처 설계 및 적용

**진행 방식** — 먼저 **현재 구조의 문제(AS-IS)를 정의**하는 것에서 시작했습니다. 추론이 FastAPI 요청 경로 안에서 동기 실행되어 ① 동시 요청 시 응답 지연 ② 같은 이미지의 중복 추론 ③ 웹 프로세스마다 모델이 중복 적재되어 확장 불가 ④ 프로세스가 죽으면 작업 유실, 네 가지 문제가 있었습니다.

이를 **Event-Driven Architecture**로 해결하는 설계를 [문서로 정리](docs/9일차_동시성문제_해결을위한_아키텍처설계.md)했습니다.

- 표준 패턴 3가지로 구조를 잡았습니다: **Queue-Based Load Leveling**(큐가 완충재), **Competing Consumers**(워커 N개가 한 큐를 나눠 처리), **Asynchronous Request-Reply**(접수 후 상태 폴링).
- Redis 활용 방식을 Pub/Sub · List · Streams로 비교하고, 그 위의 Celery까지 장단점을 표로 정리한 뒤 권장안을 선택했습니다.

**실제 적용된 것**

- 추론을 FastAPI 프로세스 밖으로 완전히 들어냈습니다. 이제 `worker/model.py`를 import 하는 주체는 워커뿐이고, 웹 이미지에는 torch가 아예 설치되지 않습니다.
- Redis List를 작업 큐로 사용하되, `BLMOVE`로 처리 중 리스트에 옮겨 **워커가 죽어도 작업이 유실되지 않게** 했고, 재기동 시 미완료 작업을 회수합니다.
- `SET NX`로 멱등키를 잡아 **같은 진료기록에 대한 동시 요청이 중복 추론을 일으키지 않도록** 했습니다.
- `docker compose up -d --scale ai-worker=3` 으로 워커만 독립 증설할 수 있습니다.

**아직 적용하지 못한 것** — 설계서의 결론인 **`202 Accepted` + 작업 상태 폴링**은 적용하지 못했습니다. 현재 예측 API는 워커에 작업을 넘긴 뒤 그 결과를 **요청 안에서 최대 60초 기다립니다.** 추론 부하는 분리됐지만, 클라이언트 입장의 응답 시간 목표(NFR-PRED-002, 3초)는 최초 추론 요청에서 여전히 지키지 못합니다. 요구사항 정의서에 **OPEN-02**로 남겨 두었습니다.

**배운 점** — 설계 문서를 쓰는 것과 그 설계를 코드에 반영하는 것 사이에는 큰 간극이 있습니다. 문서에서 "권장"이라고 결론 내린 것이 자동으로 구현되지는 않으며, **설계서의 완료 조건을 체크리스트로 만들어 구현 PR에서 확인**했어야 했습니다.

## 8. 도커 인프라 관련 파일 작성

**진행 방식** — `fastapi` / `ai-worker` / `mysql` / `redis` 4개 서비스를 compose로 구성하고, 웹과 워커의 **Dockerfile과 의존성을 분리**했습니다.

- `pyproject.toml`의 optional-dependencies를 `app`(웹)과 `ai`(추론)로 나누고, torch는 **CPU 전용 wheel**만 받도록 인덱스를 지정했습니다. 기본 인덱스는 CUDA 런타임까지 끌어와 이미지가 수 GB가 됩니다.
- `depends_on` + `healthcheck`로 MySQL·Redis가 준비된 뒤 앱이 뜨도록 기동 순서를 보장했습니다.

**막혔던 지점들** — [8일차 문서](docs/8일차_Docker_컨테이너화.md)에 6가지 실패와 해결을 남겼습니다. `asyncmy` 소스 빌드에 gcc가 없어 실패한 것, 볼륨 마운트 경로가 프로젝트 구조와 어긋난 것, 컨테이너 안에서는 DB 호스트가 `localhost`가 아니라 서비스명이어야 하는 것, healthcheck에 쓸 `curl`이 이미지에 없던 것 등입니다.

**배운 점** — 로컬에서 되는 것과 컨테이너에서 되는 것은 다릅니다. 특히 **"내 PC 기준 설정값"(localhost, 포트)이 컨테이너 네트워크에서 깨진다**는 점이 반복해서 문제가 됐습니다.

## 9. AWS 배포

**현재 상태: 미진행.** 이번 프로젝트에서 완료하지 못한 단계입니다.

배포를 위해 **이미 준비된 것**과 **남은 일**을 구분해 기록합니다.

| 준비된 것 | 남은 일 |
| --- | --- |
| compose 기반으로 전체 스택이 한 번에 기동됨 | 운영용 compose 분리(`--reload` 제거, 소스 볼륨 마운트 제거) |
| 비밀 값이 `.env`로 분리되어 있음 (`.env.example`만 커밋) | 서버에서의 `.env` 주입 방식 결정 |
| 웹·워커 이미지가 분리되어 워커만 증설 가능 | 이미지 레지스트리(ECR 등) 및 배포 자동화 |
| PR 단위 테스트 CI 존재 | 배포 CD 파이프라인 |

**미리 확인된 제약** — 리프레시 토큰 쿠키가 `secure=true`이므로, **HTTP로만 노출되는 서버에 배포하면 토큰 재발급이 동작하지 않습니다.** 브라우저는 `localhost`만 예외로 취급하기 때문입니다. 따라서 배포 시 HTTPS 구성이 선택이 아니라 전제입니다. (요구사항 정의서 `REQ-OPS-005`)

## 전체 회고

**잘된 점**

1. **문서를 남기며 진행했습니다.** 단순 결과물이 아니라 막힌 지점과 해결 과정(도커 6건, 아키텍처 문제 정의)을 남겨, 나중에 합류해도 맥락을 따라올 수 있습니다.
2. **요구사항 ID로 문서와 코드를 연결했습니다.** 코드 주석의 `REQ-USER-001`이 명세서의 항목과 이어져 추적이 가능합니다.
3. **PR 리뷰가 실제로 작동했습니다.** main 병합 11건 전부 PR을 거쳤고, 리뷰에서 실제 결함이 수정됐습니다.

**아쉬운 점**

1. **요구사항 정의서를 우리 손으로 먼저 쓰지 않았습니다.** 읽고 인용만 하다 보니, 합의된 적 없는 동작(OPEN-01~04)이 구현에 들어간 뒤에야 드러났습니다.
2. **설계와 구현 사이에 간극이 남았습니다.** 9일차 설계의 핵심인 비동기 응답이 아직 적용되지 않았습니다.
3. **마지막 두 단계(배포·QA)에 시간을 배분하지 못했습니다.** 기능 구현이 일정 후반까지 이어지면서 배포와 테스트가 밀렸습니다.

**다음 프로젝트에 가져갈 것**

1. 요구사항 정의서를 **1일차 산출물**로 만들고, 판단이 필요한 항목은 처음부터 미결 사항으로 분리해 팀 결정을 받는다.
2. 명세를 나눠 쓰기 전에 **공통 규약(페이지네이션·에러 형식·인증 방식)을 먼저 확정**한다.
3. 설계 문서의 완료 조건을 **구현 PR의 체크리스트**로 옮겨, 문서와 코드가 갈라지지 않게 한다.
4. 브랜치 네이밍 규칙을 팀 규칙에 포함시킨다.
5. 배포와 QA를 마지막에 몰지 않고, **기능 하나가 끝날 때마다 테스트를 함께 병합**한다.
