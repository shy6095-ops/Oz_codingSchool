## 1. 서비스 개요

병원 내부 사용자가 환자와 진료기록을 관리하고, 진료기록에 첨부된 흉부 X-ray 이미지에 대해 **AI 폐렴 예측 결과를 확인**할 수 있는 웹 서비스다.
AI 추론은 웹 요청 처리와 분리된 **별도의 AI 워커 프로세스**가 담당하며, FastAPI 와 워커는 Redis 를 통해 작업을 주고받는다.

### 1.1 사용자(액터) 정의

| 액터 | 설명 | 시스템상 표현 |
| --- | --- | --- |
| 비회원 | 가입/로그인만 가능 | 토큰 없음 |
| 대기 회원 | 가입 직후, 관리자 승인 대기 상태 | `role = PENDING` |
| 일반 직원 | 승인된 사용자 | `role = STAFF` |
| 관리자 | 회원 목록 조회 및 권한 변경 가능 | `role = ADMIN` |
| 의료 부서 사용자 | 환자·진료기록을 **등록**할 수 있는 사용자 | `department = MEDICAL` |
| 개발/연구 부서 사용자 | 환자·진료기록 조회 및 AI 예측 조회 | `department = DEV` / `RESEARCH` |

> 권한은 **역할(`role`)** 과 **부서(`department`)** 두 축으로 나뉜다.
> - 관리자 전용 기능은 `role = ADMIN` 으로 통제한다.
> - 등록(쓰기) 기능은 `department = MEDICAL` 로 통제한다.
> - 조회 기능은 로그인 여부만 확인한다.

### 1.2 용어 정의

| 용어 | 정의 |
| --- | --- |
| 환자(Patient) | 진료 대상자. 이름·나이·성별·연락처를 가진다. |
| 진료기록(Medical Record) | 특정 환자의 1회 진료 내역. 차트번호·증상을 가지며 X-ray 이미지를 선택적으로 첨부한다. |
| X-ray 이미지 | 진료기록에 첨부된 흉부 X-ray 파일. 서버 로컬 `media/xrays/` 에 저장한다. |
| AI 예측 결과 | 특정 진료기록의 X-ray 에 대한 폐렴 여부(`is_pneumonia`)와 신뢰도(`confidence`). |
| AI 워커 | 추론 전용 프로세스. Redis 큐에서 작업을 꺼내 추론 후 결과를 반환한다. |

### 1.3 요구사항 ID 체계

`REQ-{도메인}-{일련번호}` (기능 요구사항), `NFR-{도메인}-{일련번호}` (비기능 요구사항)

| 도메인 코드 | 범위 |
| --- | --- |
| `USER` | 회원가입 · 인증 · 회원 관리 |
| `PTNT` | 환자 관리 |
| `MDR` | 진료기록 관리 |
| `PRED` | AI 폐렴 예측 |
| `OPS` | 배포 · 운영 (팀 자체 정의) |

우선순위: **M**(Must, 필수) / **S**(Should, 권장) / **C**(Could, 선택)

## 2. 기능 요구사항 — 회원 · 인증 (USER)

| ID | 요구사항 | 우선순위 | 액터 |
| --- | --- | --- | --- |
| REQ-USER-001 | 사용자는 이메일·비밀번호·이름·부서·성별·휴대폰번호로 **회원가입**할 수 있다. | M | 비회원 |
| REQ-USER-002 | 사용자는 이메일과 비밀번호로 **로그인**하여 인증 토큰을 발급받는다. | M | 비회원 |
| REQ-USER-003 | 사용자는 **로그아웃**하여 발급된 인증 상태를 해제할 수 있다. | M | 전체 회원 |
| REQ-USER-004 | 관리자는 **회원 목록을 조회**하고 이메일/이름 검색과 부서 필터를 적용할 수 있다. | M | 관리자 |
| REQ-USER-005 | 관리자는 회원의 **권한(역할)을 변경**할 수 있다. | M | 관리자 |
| REQ-USER-006 | 사용자는 **본인 정보(마이페이지)를 조회**할 수 있다. | M | 전체 회원 |
| REQ-USER-007 | 사용자는 본인의 **부서와 휴대폰번호를 수정**할 수 있다. | S | 전체 회원 |
| REQ-USER-008 | 사용자는 기존 비밀번호 확인 후 **비밀번호를 변경**할 수 있다. | S | 전체 회원 |
| REQ-USER-009 | 사용자는 **회원 탈퇴**할 수 있다. | S | 전체 회원 |

### 2.1 인수 조건

**REQ-USER-001 회원가입**
- 필수 입력: `email`(형식 검증), `password`(8~64자), `name`(1~20자), `department`(`MEDICAL`/`DEV`/`RESEARCH`), `gender`(`M`/`F`), `phone_number`(`01[016789]-?xxx(x)-?xxxx` 형식, 최대 20자)
- 가입 성공 시 역할은 항상 `PENDING` 으로 부여된다. (관리자 승인 전제 — REQ-USER-005 와 연결)
- 비밀번호는 평문으로 저장하지 않는다. (NFR-USER-001)
- 이미 사용 중인 **이메일** 또는 **휴대폰번호**로 가입하면 거부된다.

**REQ-USER-002 로그인**
- 이메일 또는 비밀번호가 틀리면 **어느 쪽이 틀렸는지 구분하지 않고** 동일한 실패 응답을 준다. (계정 존재 여부 노출 방지)
- 비활성 계정(`is_active = false`)은 로그인할 수 없다.
- 성공 시 액세스 토큰은 응답 본문으로, 리프레시 토큰은 브라우저 스크립트가 읽을 수 없는 형태로 전달된다. (NFR-USER-001)

**REQ-USER-003 로그아웃**
- 로그인 상태에서만 호출할 수 있고, 서버가 내려준 리프레시 토큰 쿠키를 제거한다.

**REQ-USER-004 회원 목록 조회**
- 관리자가 아닌 사용자의 요청은 거부된다.
- 검색어는 이메일 또는 이름에 대해 부분 일치로 동작하며, 부서 필터와 함께 적용할 수 있다.
- 페이지네이션은 `offset`(0 이상) / `limit`(1~100, 기본 20)을 사용하고, 전체 건수(`total`)를 함께 반환한다.

**REQ-USER-005 회원 권한 변경**
- 관리자만 대상 회원의 역할을 `PENDING` / `STAFF` / `ADMIN` 중 하나로 변경할 수 있다.
- 존재하지 않는 회원을 대상으로 하면 거부된다.

**REQ-USER-006 마이페이지 조회**
- 로그인한 본인의 `id`, `email`, `name`, `department`, `gender`, `phone_number`, `role`, `is_active`, `created_at` 을 반환한다. 비밀번호 해시는 절대 반환하지 않는다.

**REQ-USER-007 회원 정보 수정**
- 수정 가능한 항목은 **부서와 휴대폰번호뿐**이다. 이메일·이름·역할은 본인이 변경할 수 없다.
- 수정할 항목을 하나도 보내지 않으면 거부된다.
- 다른 회원이 사용 중인 휴대폰번호로는 변경할 수 없다.

**REQ-USER-008 비밀번호 변경**
- 기존 비밀번호가 일치해야 하며, 새 비밀번호는 8~64자여야 한다.

**REQ-USER-009 회원 탈퇴**
- 탈퇴 시 회원 데이터를 삭제하고 리프레시 토큰 쿠키를 제거한다.

### 2.2 비기능 요구사항

| ID | 요구사항 | 검증 기준 |
| --- | --- | --- |
| NFR-USER-001 | 인증은 JWT 기반으로 하며, 토큰이 탈취·노출되기 어려운 방식으로 관리한다. | ① 비밀번호는 bcrypt 해시로 저장 ② 액세스 토큰 30분 / 리프레시 토큰 7일 만료 ③ 리프레시 토큰은 `httponly` + `secure` + `samesite=lax` 쿠키로만 전달하고 경로를 재발급 엔드포인트로 제한 ④ 토큰 페이로드에는 `sub`(user_id) · `type` · `iat` · `exp` 외의 개인정보를 담지 않음 ⑤ 액세스 토큰으로 재발급을, 리프레시 토큰으로 API 호출을 시도하면 거부(`type` 검증) |

## 3. 기능 요구사항 — 환자 관리 (PTNT)

| ID | 요구사항 | 우선순위 | 액터 |
| --- | --- | --- | --- |
| REQ-PTNT-001 | 의료 부서 사용자는 **환자를 등록**할 수 있다. | M | 의료 부서 |
| REQ-PTNT-002 | 로그인 사용자는 **환자 목록을 조회**하고 이름·성별·나이 범위로 검색할 수 있다. | M | 전체 회원 |
| REQ-PTNT-003 | 로그인 사용자는 **환자 상세 정보를 조회**할 수 있다. | M | 전체 회원 |
| REQ-PTNT-004 | 로그인 사용자는 환자의 **이름·연락처를 수정**할 수 있다. | S | 전체 회원 |
| REQ-PTNT-005 | 로그인 사용자는 **환자를 삭제**할 수 있다. | S | 전체 회원 |

### 3.1 인수 조건
- 환자 정보는 `name`(최대 30자), `age`(0~130), `gender`(`M`/`F`), `phone_number`(최대 20자)로 구성된다. (REQ-PTNT-001)
- 등록은 의료 부서 사용자만 가능하며, 비로그인은 인증 실패, 타 부서는 권한 없음으로 거부된다. (REQ-PTNT-001)
- 목록 조회는 이름 부분검색·성별·나이 범위 필터와 페이지네이션(`page` 기본 1, `size` 1~100 기본 20)을 지원하고, `min_age > max_age` 인 요청은 거부한다. (REQ-PTNT-002)
- 존재하지 않는 환자에 대한 조회·수정·삭제는 "찾을 수 없음"으로 응답한다. (REQ-PTNT-003~005)
- 수정은 이름/연락처 중 최소 한 항목을 포함해야 하며, 빈 수정 요청은 거부한다. (REQ-PTNT-004)
- 환자를 삭제하면 그 환자의 **진료기록·X-ray 이미지 레코드·AI 분석 결과**가 함께 삭제되고, 서버에 저장된 이미지 파일도 삭제된다. (REQ-PTNT-005)

### 3.2 비기능 요구사항

| ID | 요구사항 | 검증 기준 |
| --- | --- | --- |
| NFR-PTNT-001 | 환자 조회·검색 응답은 3초 이내에 완료한다. | 목록 조회는 페이지 범위만 조회하고, 이미지 바이너리는 응답에 포함하지 않고 URL 만 반환 |

## 4. 기능 요구사항 — 진료기록 (MDR)

| ID | 요구사항 | 우선순위 | 액터 |
| --- | --- | --- | --- |
| REQ-MDR-001 | 의료 부서 사용자는 환자에게 **진료기록을 등록**하고 X-ray 이미지를 첨부할 수 있다. | M | 의료 부서 |
| REQ-MDR-002 | 로그인 사용자는 **환자별 진료기록 목록을 최신순으로 조회**할 수 있다. | M | 전체 회원 |
| REQ-MDR-003 | 로그인 사용자는 **진료기록 상세와 첨부 X-ray 이미지를 조회**할 수 있다. | M | 전체 회원 |

### 4.1 인수 조건
- 진료기록은 `chart_number`(최대 50자)와 `symptoms` 를 필수로 하고, X-ray 이미지는 선택 첨부다. (REQ-MDR-001)
- 첨부 파일은 JPG/JPEG/PNG 만 허용하며, 빈 파일·이미지가 아닌 파일·미지원 확장자는 거부한다. (REQ-MDR-001)
- 업로드된 파일은 원본 파일명을 쓰지 않고 UUID 로 이름을 새로 생성해 `media/xrays/` 에 저장한다. (REQ-MDR-001, 파일명 충돌·경로 조작 방지)
- 이미지를 첨부하지 않은 기록의 이미지 URL 은 `null` 로 응답한다. (REQ-MDR-001, REQ-MDR-003)
- 목록은 최신 진료기록부터 정렬하고 페이지네이션을 지원한다. 화면에서는 증상이 100자를 넘으면 말줄임 처리한다. (REQ-MDR-002)
- 존재하지 않는 환자/진료기록에 대한 요청은 "찾을 수 없음"으로 응답한다. (REQ-MDR-001~003)

### 4.2 비기능 요구사항

| ID | 요구사항 | 검증 기준 |
| --- | --- | --- |
| NFR-MDR-001 | 진료기록 등록·조회 응답은 3초 이내에 완료한다. | 파일 저장/삭제 등 동기 I/O 는 이벤트 루프를 막지 않도록 별도 스레드로 위임(`asyncio.to_thread`) |

## 5. 기능 요구사항 — AI 폐렴 예측 (PRED)

| ID | 요구사항 | 우선순위 | 액터 |
| --- | --- | --- | --- |
| REQ-PRED-001 | 로그인 사용자는 진료기록의 X-ray 에 대해 **AI 폐렴 예측을 실행**하고 결과(폐렴 여부·신뢰도)를 확인할 수 있다. | M | 전체 회원 |
| REQ-PRED-002 | 로그인 사용자는 해당 진료기록에 대해 **수행된 예측 결과 목록을 조회**할 수 있다. | M | 전체 회원 |

### 5.1 인수 조건
- 예측 결과는 폐렴 여부(`is_pneumonia`), 신뢰도(`confidence`), 사용 모델명(`ai_model`), 생성 시각을 포함한다. (REQ-PRED-001)
- **같은 진료기록 + 같은 모델**로 이미 저장된 결과가 있으면 재추론하지 않고 저장된 결과를 반환한다. (REQ-PRED-001, NFR-PRED-002)
- 진료기록에 X-ray 이미지가 없으면 예측을 실행할 수 없다. (REQ-PRED-001)
- 한 진료기록에 X-ray 가 여러 장이면 **가장 최근 이미지**로 예측한다. (REQ-PRED-001)
- 히트맵(`heatmap_url`)은 선택 항목이며 현재 구현에서는 `null` 이다. (Grad-CAM 은 확장 과제)
- 존재하지 않는 진료기록에 대한 요청은 "찾을 수 없음"으로 응답한다. (REQ-PRED-001~002)

### 5.2 비기능 요구사항

| ID | 요구사항 | 검증 기준 |
| --- | --- | --- |

## 7. 미결 사항 (Open Issues)

구현과 요구사항 사이에 **아직 팀 결정이 필요한 항목**이다. 임의로 정하지 않고 분리해 둔다.

| ID | 내용 | 현재 동작 | 결정 필요 |
| --- | --- | --- | --- |
| OPEN-01 | `role = PENDING`(승인 대기) 사용자의 접근 범위 | 가입 직후 `PENDING` 이지만, 로그인과 대부분의 API 사용이 가능하다. 실제로 역할이 통제하는 것은 관리자 전용 API 뿐이다. | "승인 전에는 조회도 불가" 로 할지, 현재처럼 관리자 기능만 막을지 |
| OPEN-02 | 예측 API 의 응답 방식 | [9일차 아키텍처 설계](9일차_동시성문제_해결을위한_아키텍처설계.md)는 `202 Accepted` + 작업 상태 폴링을 권장안으로 결론냈으나, 현재 구현은 요청 안에서 워커 결과를 최대 60초 대기한다. | 설계안대로 비동기 응답으로 전환할지, 현행 유지할지 (NFR-PRED-002 충족 여부와 직결) |
| OPEN-03 | 환자 수정·삭제 권한 | 등록은 의료 부서 전용이지만, **수정·삭제는 로그인만 하면 누구나** 가능하다. | 수정·삭제도 의료 부서로 제한할지 |
| OPEN-04 | 회원 탈퇴 방식 | 데이터를 실제로 삭제(hard delete)한다. | 의료 도메인 특성상 비활성화(`is_active = false`)로 남길지 |
