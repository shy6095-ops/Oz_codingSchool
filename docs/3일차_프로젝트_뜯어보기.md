1. 각 디렉터리는 어떤 역할을 수행하며, 작성해야 할 파일의 내용

| 디렉터리 | 역할 및 작성하는 내용 |
|---|---|
| `app/core/` | 애플리케이션 전체에서 공통으로 사용하는 핵심 설정과 기능을 관리합니다. 환경변수, 데이터베이스 연결 설정, 보안 및 인증 관련 설정 등 여러 기능에서 공통으로 필요한 코드가 들어갑니다. 예를 들어 `config.py`에서는 환경변수와 프로젝트 설정을 관리하고, `db/`에서는 SQLAlchemy를 이용한 데이터베이스 연결을 설정할 수 있습니다. |
| `app/models/` | 데이터베이스의 테이블 구조를 Python 클래스로 정의하는 곳입니다. 주로 SQLAlchemy ORM 모델을 작성하며, 테이블 이름과 `id`, `name`, `email` 등의 컬럼, 데이터 타입, Primary Key, Foreign Key, 테이블 간 관계 등을 정의합니다. 즉 실제 DB의 테이블이 Python에서는 어떤 구조로 사용될지를 표현하는 계층입니다. |
| `app/repositories/` | 데이터베이스에 직접 접근하여 데이터를 조회·생성·수정·삭제하는 코드를 작성합니다. 예를 들어 `id로 회원 찾기`, `새 회원 저장`, `회원 정보 수정`, `회원 삭제` 등의 CRUD 작업을 담당합니다. Service가 "회원 정보를 찾아줘"라고 요청하면 Repository가 SQLAlchemy를 이용하여 실제 DB와 통신하는 구조입니다. |
| `app/schemas/` | API에서 주고받는 데이터의 구조와 검증 규칙을 정의합니다. FastAPI에서는 주로 Pydantic 모델을 사용합니다. 예를 들어 회원가입 API에서 `name`, `email`, `password`를 입력받도록 정의하거나, 응답에서는 `password`를 제외하고 `id`, `name`, `email`만 반환하도록 정의할 수 있습니다. 데이터 타입, 필수 여부, 길이 등의 유효성 검증에도 사용됩니다. |
| `app/services/` | 애플리케이션의 실제 업무 규칙인 비즈니스 로직을 처리합니다. API에서 요청을 전달받아 필요한 처리를 수행하고 Repository를 호출합니다. 예를 들어 회원가입에서는 `이메일 중복 확인 → 비밀번호 처리 → Repository를 통한 회원 저장` 등의 과정을 담당할 수 있습니다. API와 DB 접근 코드를 분리하여 복잡한 로직을 관리하기 쉽게 만드는 역할을 합니다. |
| `app/apis/` | 클라이언트의 HTTP 요청을 직접 받는 API endpoint와 Router를 작성합니다. `GET`, `POST`, `PATCH`, `DELETE` 등의 HTTP Method와 URL을 정의하고 Path Parameter, Query Parameter, Request Body 등을 전달받습니다. 요청받은 데이터를 Service에 전달하고 처리 결과를 HTTP 응답으로 반환합니다. 작성된 `APIRouter`는 최종적으로 `main.py`의 FastAPI 애플리케이션에 등록됩니다. |

### * 디렉터리 간 관계

클라이언트의 요청이 들어오면 일반적으로 다음과 같은 흐름으로 처리됩니다.

`Client → API → Schema → Service → Repository → Model → Database`

- **API**: HTTP 요청을 받고 응답을 반환
- **Schema**: 요청 및 응답 데이터의 형식과 유효성을 검사
- **Service**: 실제 비즈니스 로직을 수행
- **Repository**: 데이터베이스에 필요한 작업을 요청
- **Model**: 데이터베이스 테이블의 구조를 정의
- **Database**: 실제 데이터를 저장하고 관리

`core`는 위 흐름의 한 단계라기보다는 데이터베이스 연결이나 환경설정처럼 애플리케이션 전체에서 필요한 공통 기능을 제공합니다.
**[수정: 마크다운 렌더링 시 과도한 여백을 유발하는 `<br>` 태그를 모두 제거하고 기본 줄바꿈으로 통일했습니다.]**

## 2. 각 파일의 역할

| 파일 | 역할 |
|---|---|
| `app/main.py` | FastAPI 애플리케이션의 **시작점(Entry Point)**입니다. `FastAPI()` 객체를 생성하고, 각 디렉터리에서 작성한 API Router를 `include_router()`를 통해 하나의 애플리케이션에 등록합니다. 또한 정적 파일 경로 설정, 미들웨어 등록 등 애플리케이션 전체에 적용되는 기능을 설정할 수 있습니다. 서버를 실행하면 이 파일을 중심으로 FastAPI 애플리케이션이 동작합니다. |
| `app/core/config.py` | 프로젝트에서 사용하는 **환경설정 값을 중앙에서 관리**하는 파일입니다. 데이터베이스 주소, 프로젝트 환경변수 등 실행 환경에 따라 달라질 수 있는 설정을 관리합니다. 설정값을 여러 파일에 직접 작성하지 않고 `config.py`를 통해 관리하면 설정 변경과 유지보수가 쉬워지고 중요한 설정값을 코드와 분리하여 관리할 수 있습니다. |
| `pyproject.toml` | Python 프로젝트의 **프로젝트 정보, 실행 환경 및 의존성(Dependency)을 정의하는 설정 파일**입니다. FastAPI, SQLAlchemy, Alembic 등 프로젝트에서 어떤 라이브러리를 사용하는지와 필요한 버전 범위를 정의할 수 있습니다. 개발 도구의 설정도 이 파일에서 관리할 수 있어 프로젝트 환경을 다른 개발자와 공유하는 기준이 됩니다. |
| `uv.lock` | `pyproject.toml`의 의존성을 바탕으로 실제 설치되는 **라이브러리와 하위 의존성의 정확한 버전을 기록하여 고정하는 파일**입니다. 같은 `pyproject.toml`을 사용하더라도 설치 시점에 따라 라이브러리 버전이 달라질 수 있는데, `uv.lock`을 이용하면 팀원들이 동일한 버전의 패키지를 설치하여 최대한 동일한 개발 환경을 구성할 수 있습니다. 일반적으로 개발자가 직접 내용을 수정하기보다 `uv`가 자동으로 생성·관리합니다. |

### * `pyproject.toml`과 `uv.lock`의 차이

- `pyproject.toml` : 프로젝트가 **어떤 라이브러리를 필요로 하는지** 정의합니다.
- `uv.lock` : 그 조건에 따라 실제로 설치할 **정확한 라이브러리 버전과 하위 의존성까지 기록**합니다.

예를 들어 `pyproject.toml`이 프로젝트에 필요한 패키지의 조건을 정하는 파일이라면,
`uv.lock`은 실제 설치 환경을 재현하기 위해 구체적인 패키지 버전을 기록해 둔 파일이라고 볼 수 있습니다.

## 3. 데이터베이스 연결 설정

### `app/core/db/database.py` **[수정: 파일명 관례에 따라 복수형(databases)에서 단수형(database)으로 변경했습니다.]**

- FastAPI 애플리케이션과 데이터베이스를 연결하기 위한 설정을 관리하는 파일입니다.

- SQLAlchemy를 사용하는 경우 일반적으로 **DB 접속 주소 설정 → Engine 생성 → Session 생성 → FastAPI에서 Session 사용 및 반환**의 흐름으로 데이터베이스에 접근합니다. **[수정: 'Session 사용 및 반환'으로 문구 보완]**

- **DB URL(Database URL)**은 애플리케이션이 어떤 데이터베이스에 접속할 것인지 알려주는 주소입니다. 사용하는 DB 종류와 서버 주소, 계정 정보, 데이터베이스 이름 등의 접속 정보가 포함될 수 있습니다.

- **Engine**은 SQLAlchemy와 실제 데이터베이스 사이의 연결을 관리합니다. Python 애플리케이션이 데이터베이스와 통신할 수 있도록 연결 통로 역할을 하며, 필요한 DB 연결을 생성하고 관리합니다.

- **Session**은 Engine을 통해 데이터베이스와 실제 데이터를 주고받을 때 사용하는 작업 단위입니다. SQLAlchemy 모델을 이용하여 데이터의 조회(SELECT), 추가(INSERT), 수정(UPDATE), 삭제(DELETE) 등의 작업을 수행할 수 있습니다.

- FastAPI에서는 API 요청이 들어올 때 의존성 주입(`Depends`)과 제너레이터(`yield`)를 사용하여 Session을 생성합니다. 요청 처리가 끝난 후에는 성공 여부와 관계없이 `finally` 블록을 통해 Session을 확실하게 `close()` 하여 데이터베이스 연결 누수(Leak)를 방지하고 커넥션 풀(Connection Pool)로 안전하게 반환합니다. **[추가: DB 세션의 의존성 주입(Depends), yield, 그리고 finally 블록을 통한 안전한 종료 및 반환 메커니즘 상세 설명 추가]**

### * 데이터베이스 연결 흐름

`FastAPI → DB Session 주입 → SQLAlchemy Engine → Database → 로직 처리 후 Session 반환(close)` **[수정: 흐름도 마지막에 Session 반환 과정 추가]**

예를 들어 회원 조회 API에 요청이 들어오면 다음과 같은 흐름으로 처리될 수 있습니다.

`회원 조회 요청 → API → 의존성 주입(Session 할당) → Service → Repository → Engine → Database` **[수정: 흐름도에 의존성 주입 단계 명시]**

데이터베이스에서 조회된 결과는 반대 방향으로 전달되어 최종적으로 FastAPI가 클라이언트에게 응답합니다.

## 4. SQLAlchemy를 활용하여 모델을 작성하고 Alembic을 활용하여 마이그레이션을 수행하는 방법

### SQLAlchemy와 Alembic의 역할

- **SQLAlchemy**는 데이터베이스의 테이블을 Python 클래스 형태로 정의하고, Python 코드에서 데이터베이스를 조회·추가·수정·삭제할 수 있도록 도와주는 라이브러리입니다.
- **Model**은 SQLAlchemy를 이용하여 실제 데이터베이스 테이블의 구조를 Python 코드로 표현한 것입니다.
- **Alembic**은 SQLAlchemy Model의 변경사항을 추적하여 실제 데이터베이스의 테이블 구조에 반영하는 마이그레이션 도구입니다.
- 즉, SQLAlchemy가 **DB 구조를 Python 코드로 정의**한다면, Alembic은 **그 구조의 변경사항을 실제 DB에 적용하고 버전별로 관리**하는 역할을 합니다.

### 1) SQLAlchemy Model 작성

`app/models/` 디렉터리에 데이터베이스 테이블과 대응되는 Model을 작성합니다.

예를 들어 User 테이블이 있다면 다음과 같은 정보를 Model에 정의할 수 있습니다.

- 테이블 이름
- `id`, `name`, `email` 등의 컬럼
- 각 컬럼의 데이터 타입
- Primary Key
- Foreign Key
- 테이블 간 Relationship
- NULL 허용 여부 및 기타 제약조건

Model을 수정하는 것은 Python 코드상의 테이블 구조를 변경하는 것이며, 이것만으로 실제 데이터베이스의 테이블 구조가 자동으로 변경되는 것은 아닙니다.

### 2) Alembic Migration 파일 생성

Model을 새로 생성하거나 기존 Model의 컬럼 등을 변경했다면 Alembic을 이용하여 변경사항을 Migration 파일로 생성합니다.

일반적으로 다음과 같은 명령어를 사용할 수 있습니다.

`alembic revision --autogenerate -m "migration message"`

Alembic은 SQLAlchemy Model의 구조와 현재 데이터베이스 구조를 비교하여 필요한 변경사항을 Migration 파일에 기록합니다.

### 3) Migration 내용 확인

자동으로 생성된 Migration 파일의 내용을 확인합니다.

일반적으로 Migration 파일에는 다음과 같은 함수가 생성됩니다.

- `upgrade()` : 새로운 변경사항을 데이터베이스에 적용
- `downgrade()` : 적용했던 변경사항을 이전 상태로 되돌림

자동 생성된 내용이 항상 개발자의 의도와 정확하게 일치한다고 보장할 수 없기 때문에 실제 DB에 적용하기 전에 내용을 확인하는 것이 중요합니다.

### 4) 실제 데이터베이스에 적용

Migration 파일을 확인한 후 다음 명령어를 사용하여 실제 데이터베이스에 변경사항을 적용할 수 있습니다.

`alembic upgrade head`

`head`는 현재 존재하는 Migration 중 가장 최신 버전을 의미하며, 이 명령을 실행하면 DB가 최신 Migration 상태까지 업데이트됩니다.

### * 전체 흐름

`SQLAlchemy Model 작성/수정 → Alembic Migration 생성 → Migration 내용 확인 → DB에 Migration 적용`

예를 들어 기존 User 테이블에 `age` 컬럼을 추가한다면 다음과 같은 과정으로 진행됩니다.

`User Model에 age 추가 → Alembic Migration 생성 → 생성된 Migration 확인 → alembic upgrade head 실행 → 실제 User 테이블에 age 컬럼 반영`

## 5. API 구현 흐름

FastAPI 프로젝트에서 사용자의 요청은 API에서 시작하여 여러 계층을 거쳐 데이터베이스까지 전달됩니다.
각 계층은 역할을 나누어 담당하며, 데이터베이스에서 처리된 결과는 다시 반대 방향으로 전달되어 사용자에게 응답됩니다.

### * 전체 흐름

`사용자(Client) → API → Schema → Service → Repository → SQLAlchemy Model → Database`

데이터베이스에서 작업이 완료되면 결과는 다시 다음과 같은 흐름으로 사용자에게 전달됩니다.

`Database → Model → Repository → Service → API → Schema(직렬화) → 사용자(Client)` **[수정: 응답 반환 흐름에 Schema를 통한 직렬화 과정 명시]**

### * 단계별 역할

1. **사용자(Client)**
   - 브라우저, 애플리케이션, Swagger UI 등의 클라이언트에서 FastAPI 서버로 HTTP 요청을 보냅니다.
   - `GET`, `POST`, `PATCH`, `DELETE` 등의 HTTP Method를 이용하여 데이터 조회, 생성, 수정, 삭제를 요청할 수 있습니다.

2. **API - `app/apis/`**
   - 사용자의 HTTP 요청을 가장 먼저 받는 영역입니다.
   - URL(endpoint)과 HTTP Method를 정의하고 Path Parameter, Query Parameter, Request Body 등의 데이터를 전달받습니다.
   - 전달받은 요청을 필요한 Schema나 Service에 전달하고 최종 처리 결과를 HTTP 응답으로 반환합니다.

3. **Schema - `app/schemas/`**
   - API에서 입력받거나 반환할 데이터의 구조와 형식을 정의합니다.
   - FastAPI에서는 주로 Pydantic을 사용하여 데이터 타입, 필수 입력 여부, 길이 등의 유효성을 검증합니다.
   - 잘못된 형식의 데이터가 비즈니스 로직이나 데이터베이스까지 전달되는 것을 방지합니다. 또한, DB에서 반환된 SQLAlchemy 모델 객체를 Pydantic 스키마를 통해 JSON 형태로 직렬화(Serialization)하여 클라이언트에게 안전하고 규격화된 포맷으로 응답하는 핵심 역할을 수행합니다. **[추가: 반환 데이터의 JSON 직렬화(Serialization) 및 객체 변환 역할 상세 설명 추가]**

4. **Service - `app/services/`**
   - 애플리케이션의 실제 비즈니스 로직을 처리합니다.
   - API에서 전달받은 데이터를 바탕으로 필요한 작업을 판단하고 Repository를 호출합니다.

| `app/apis/` | 클라이언트의 HTTP 요청을 직접 받는 API endpoint와 Router를 작성합니다. `GET`, `POST`, `PATCH`, `DELETE` 등의 HTTP Method와 URL을 정의하고 Path Parameter, Query Parameter, Request Body 등을 전달받습니다. 요청받은 데이터를 Service에 전달하고 처리 결과를 HTTP 응답으로 반환합니다. 작성된 `APIRouter`는 최종적으로 `main.py`의 FastAPI 애플리케이션에 등록됩니다. |

### * 디렉터리 간 관계

클라이언트의 요청이 들어오면 일반적으로 다음과 같은 흐름으로 처리됩니다.

`Client → API → Schema → Service → Repository → Model → Database`

- **API**: HTTP 요청을 받고 응답을 반환
- **Schema**: 요청 및 응답 데이터의 형식과 유효성을 검사
- **Service**: 실제 비즈니스 로직을 수행
- **Repository**: 데이터베이스에 필요한 작업을 요청
- **Model**: 데이터베이스 테이블의 구조를 정의
- **Database**: 실제 데이터를 저장하고 관리

`core`는 위 흐름의 한 단계라기보다는 데이터베이스 연결이나 환경설정처럼 애플리케이션 전체에서 필요한 공통 기능을 제공합니다.

| 파일 | 역할 |
|---|---|
| `app/main.py` | FastAPI 애플리케이션의 **시작점(Entry Point)**입니다. `FastAPI()` 객체를 생성하고, 각 디렉터리에서 작성한 API Router를 `include_router()`를 통해 하나의 애플리케이션에 등록합니다. 또한 정적 파일 경로 설정, 미들웨어 등록 등 애플리케이션 전체에 적용되는 기능을 설정할 수 있습니다. 서버를 실행하면 이 파일을 중심으로 FastAPI 애플리케이션이 동작합니다. |
| `app/core/config.py` | 프로젝트에서 사용하는 **환경설정 값을 중앙에서 관리**하는 파일입니다. 데이터베이스 주소, 프로젝트 환경변수 등 실행 환경에 따라 달라질 수 있는 설정을 관리합니다. 설정값을 여러 파일에 직접 작성하지 않고 `config.py`를 통해 관리하면 설정 변경과 유지보수가 쉬워지고 중요한 설정값을 코드와 분리하여 관리할 수 있습니다. |
| `pyproject.toml` | Python 프로젝트의 **프로젝트 정보, 실행 환경 및 의존성(Dependency)을 정의하는 설정 파일**입니다. FastAPI, SQLAlchemy, Alembic 등 프로젝트에서 어떤 라이브러리를 사용하는지와 필요한 버전 범위를 정의할 수 있습니다. 개발 도구의 설정도 이 파일에서 관리할 수 있어 프로젝트 환경을 다른 개발자와 공유하는 기준이 됩니다. |
| `uv.lock` | `pyproject.toml`의 의존성을 바탕으로 실제 설치되는 **라이브러리와 하위 의존성의 정확한 버전을 기록하여 고정하는 파일**입니다. 같은 `pyproject.toml`을 사용하더라도 설치 시점에 따라 라이브러리 버전이 달라질 수 있는데, `uv.lock`을 이용하면 팀원들이 동일한 버전의 패키지를 설치하여 최대한 동일한 개발 환경을 구성할 수 있습니다. 일반적으로 개발자가 직접 내용을 수정하기보다 `uv`가 자동으로 생성·관리합니다. |

### * `pyproject.toml`과 `uv.lock`의 차이

- `pyproject.toml` : 프로젝트가 **어떤 라이브러리를 필요로 하는지** 정의합니다.
- `uv.lock` : 그 조건에 따라 실제로 설치할 **정확한 라이브러리 버전과 하위 의존성까지 기록**합니다.

예를 들어 `pyproject.toml`이 프로젝트에 필요한 패키지의 조건을 정하는 파일이라면, `uv.lock`은 실제 설치 환경을 재현하기 위해 구체적인 패키지 버전을 기록해 둔 파일이라고 볼 수 있습니다.

## 3. 데이터베이스 연결 설정

### `app/core/db/database.py` **[수정: 단일 설정 파일이므로 통상적으로 복수형(databases)보다 단수형(database.py) 명칭을 권장하여 파일명 오타 수정]**

- FastAPI 애플리케이션과 데이터베이스를 연결하기 위한 설정을 관리하는 파일입니다.
- SQLAlchemy를 사용하는 경우 일반적으로 **DB 접속 주소 설정 → Engine 생성 → Session 생성 → FastAPI에서 Session 사용**의 흐름으로 데이터베이스에 접근합니다.
- **DB URL(Database URL)**은 애플리케이션이 어떤 데이터베이스에 접속할 것인지 알려주는 주소입니다. 사용하는 DB 종류와 서버 주소, 계정 정보, 데이터베이스 이름 등의 접속 정보가 포함될 수 있습니다.
- **Engine**은 SQLAlchemy와 실제 데이터베이스 사이의 연결을 관리합니다. Python 애플리케이션이 데이터베이스와 통신할 수 있도록 연결 통로 역할을 하며, 필요한 DB 연결을 생성하고 관리합니다.
- **Session**은 Engine을 통해 데이터베이스와 실제 데이터를 주고받을 때 사용하는 작업 단위입니다. SQLAlchemy 모델을 이용하여 데이터의 조회(SELECT), 추가(INSERT), 수정(UPDATE), 삭제(DELETE) 등의 작업을 수행할 수 있습니다.
- FastAPI에서는 API 요청이 들어올 때 필요한 Session을 생성하여 Repository나 Service 등에서 데이터베이스 작업에 사용하고, 요청 처리가 끝난 후 Session을 종료하는 방식으로 사용할 수 있습니다.

**[추가: 세션의 안전한 반환 (Dependency Injection 활용)]**
> **[추가: FastAPI에서는 주로 `Depends(get_db)`와 같은 의존성 주입을 통해 세션을 할당받습니다. 이때 `get_db` 함수 내부에 `try ... yield ... finally` 구문을 작성하는 것이 매우 중요합니다. 로직 수행 중 에러나 예외가 발생하더라도 `finally` 블록의 `db.close()`가 무조건 실행되도록 보장하여, 사용이 끝난 DB 세션을 커넥션 풀(Connection Pool)로 안전하게 반환(종료)해야 리소스 누수(Memory/Connection Leak)를 방지할 수 있습니다.]**

### * 데이터베이스 연결 흐름

`FastAPI → DB Session 주입 → SQLAlchemy Engine → Database` **[수정: 주입 과정 명시]**

예를 들어 회원 조회 API에 요청이 들어오면 다음과 같은 흐름으로 처리될 수 있습니다.

`회원 조회 요청 → API → Service → Repository → Session → Engine → Database`

데이터베이스에서 조회된 결과는 반대 방향으로 전달되어 최종적으로 FastAPI가 클라이언트에게 응답합니다.

## 4. SQLAlchemy를 활용하여 모델을 작성하고 Alembic을 활용하여 마이그레이션을 수행하는 방법

### SQLAlchemy와 Alembic의 역할

- **SQLAlchemy**는 데이터베이스의 테이블을 Python 클래스 형태로 정의하고, Python 코드에서 데이터베이스를 조회·추가·수정·삭제할 수 있도록 도와주는 라이브러리입니다.
- **Model**은 SQLAlchemy를 이용하여 실제 데이터베이스 테이블의 구조를 Python 코드로 표현한 것입니다.
- **Alembic**은 SQLAlchemy Model의 변경사항을 추적하여 실제 데이터베이스의 테이블 구조에 반영하는 마이그레이션 도구입니다.
- 즉, SQLAlchemy가 **DB 구조를 Python 코드로 정의**한다면, Alembic은 **그 구조의 변경사항을 실제 DB에 적용하고 버전별로 관리**하는 역할을 합니다.

### 1) SQLAlchemy Model 작성

`app/models/` 디렉터리에 데이터베이스 테이블과 대응되는 Model을 작성합니다.

예를 들어 User 테이블이 있다면 다음과 같은 정보를 Model에 정의할 수 있습니다.

- 테이블 이름
- `id`, `name`, `email` 등의 컬럼
- 각 컬럼의 데이터 타입
- Primary Key
- Foreign Key
- 테이블 간 Relationship
- NULL 허용 여부 및 기타 제약조건

Model을 수정하는 것은 Python 코드상의 테이블 구조를 변경하는 것이며, 이것만으로 실제 데이터베이스의 테이블 구조가 자동으로 변경되는 것은 아닙니다.

### 2) Alembic Migration 파일 생성

Model을 새로 생성하거나 기존 Model의 컬럼 등을 변경했다면 Alembic을 이용하여 변경사항을 Migration 파일로 생성합니다.

일반적으로 다음과 같은 명령어를 사용할 수 있습니다.

`alembic revision --autogenerate -m "migration message"`

Alembic은 SQLAlchemy Model의 구조와 현재 데이터베이스 구조를 비교하여 필요한 변경사항을 Migration 파일에 기록합니다.

### 3) Migration 내용 확인

자동으로 생성된 Migration 파일의 내용을 확인합니다.

일반적으로 Migration 파일에는 다음과 같은 함수가 생성됩니다.

- `upgrade()` : 새로운 변경사항을 데이터베이스에 적용
- `downgrade()` : 적용했던 변경사항을 이전 상태로 되돌림

자동 생성된 내용이 항상 개발자의 의도와 정확하게 일치한다고 보장할 수 없기 때문에 실제 DB에 적용하기 전에 내용을 확인하는 것이 중요합니다.

### 4) 실제 데이터베이스에 적용

Migration 파일을 확인한 후 다음 명령어를 사용하여 실제 데이터베이스에 변경사항을 적용할 수 있습니다.

`alembic upgrade head`

`head`는 현재 존재하는 Migration 중 가장 최신 버전을 의미하며, 이 명령을 실행하면 DB가 최신 Migration 상태까지 업데이트됩니다.

### * 전체 흐름

`SQLAlchemy Model 작성/수정 → Alembic Migration 생성 → Migration 내용 확인 → DB에 Migration 적용`

예를 들어 기존 User 테이블에 `age` 컬럼을 추가한다면 다음과 같은 과정으로 진행됩니다.

`User Model에 age 추가 → Alembic Migration 생성 → 생성된 Migration 확인 → alembic upgrade head 실행 → 실제 User 테이블에 age 컬럼 반영`

## 5. API 구현 흐름

FastAPI 프로젝트에서 사용자의 요청은 API에서 시작하여 여러 계층을 거쳐 데이터베이스까지 전달됩니다.  
각 계층은 역할을 나누어 담당하며, 데이터베이스에서 처리된 결과는 다시 반대 방향으로 전달되어 사용자에게 응답됩니다.

### * 전체 흐름

`사용자(Client) → API → Schema → Service → Repository → SQLAlchemy Model → Database`

**[수정 및 추가: 데이터 반환 흐름 보강]**
데이터베이스에서 작업이 완료되면 결과는 다시 다음과 같은 흐름으로 사용자에게 안전하게 리턴됩니다.

`Database → Model 객체 리턴 → Repository → Service → Schema를 통한 데이터 필터링/직렬화(Response Model) → API → 사용자(Client)` 

### * 단계별 역할

1. **사용자(Client)**
   - 브라우저, 애플리케이션, Swagger UI 등의 클라이언트에서 FastAPI 서버로 HTTP 요청을 보냅니다.
   - `GET`, `POST`, `PATCH`, `DELETE` 등의 HTTP Method를 이용하여 데이터 조회, 생성, 수정, 삭제를 요청할 수 있습니다.

2. **API - `app/apis/`**
   - 사용자의 HTTP 요청을 가장 먼저 받는 영역입니다.
   - URL(endpoint)과 HTTP Method를 정의하고 Path Parameter, Query Parameter, Request Body 등의 데이터를 전달받습니다.
   - 전달받은 요청을 필요한 Schema나 Service에 전달하고 최종 처리 결과를 HTTP 응답으로 반환합니다.

3. **Schema - `app/schemas/`**
   - API에서 입력받거나 반환할 데이터의 구조와 형식을 정의합니다.
   - FastAPI에서는 주로 Pydantic을 사용하여 데이터 타입, 필수 입력 여부, 길이 등의 유효성을 검증합니다.
   - 잘못된 형식의 데이터가 비즈니스 로직이나 데이터베이스까지 전달되는 것을 방지하는 역할을 합니다.
   - **[추가: 응답 시에는 민감한 정보(예: 비밀번호)를 제외하고 안전하게 데이터를 리턴할 수 있도록, Response Model용 Schema를 분리하여 사용하는 것이 일반적입니다.]**

4. **Service - `app/services/`**
   - 애플리케이션의 실제 비즈니스 로직을 처리합니다.
   - API에서 전달받은 데이터를 바탕으로 필요한 작업을 판단하고 Repository를 호출합니다.
   - 예를 들어 회원가입의 경우 이메일 중복 확인, 비밀번호 처리 등 여러 작업을 조합하여 하나의 기능을 수행할 수 있습니다.

5. **Repository - `app/repositories/`**
   - 데이터베이스 접근을 담당하는 계층입니다.
   - SQLAlchemy의 Session과 Model 등을 이용하여 실제 데이터의 조회, 추가, 수정, 삭제(CRUD)를 수행합니다.
   - Service가 데이터베이스의 구체적인 처리 방법을 알 필요가 없도록 DB 관련 코드를 분리하는 역할을 합니다.

6. **SQLAlchemy Model - `app/models/`**
   - 데이터베이스의 테이블 구조를 Python 클래스로 표현합니다.
   - 테이블 이름, 컬럼, 데이터 타입, Primary Key, Foreign Key, 테이블 간 관계 등을 정의합니다.
   - Repository가 데이터베이스에 접근할 때 이 Model을 이용하여 데이터를 조회하거나 저장합니다.

7. **Database**
   - 실제 데이터가 저장되는 곳입니다.
   - Repository에서 전달한 요청에 따라 데이터를 조회하거나 생성·수정·삭제하고 그 결과를 반환합니다.

### 예시: 회원 조회 API

사용자가 특정 회원을 조회한다고 가정하면 다음과 같은 흐름으로 처리할 수 있습니다.

`GET /users/1 요청`
→ `API에서 요청 수신`
→ `Schema를 통한 데이터 검증 (Path Parameter 확인)` **[수정: 명확성 추가]**
→ `Service에서 회원 조회 로직 수행`
→ `Repository에서 DB 조회 요청`
→ `User Model을 이용하여 회원 데이터 조회`
→ `Database에서 결과 반환`
→ `Repository에서 ORM 객체를 Service로 전달` **[수정: 반환 데이터의 형태(ORM) 명시]**
→ `Service(또는 API)에서 ORM 객체를 Pydantic Response Schema로 변환(필요한 데이터만 리턴 포맷팅)` **[추가: 반환(Return) 시 스키마 맵핑 과정 추가]**
→ `API에서 사용자에게 최종 JSON 응답 반환`

### * 계층을 분리하는 이유

API, Service, Repository, Model 등의 역할을 분리하면 하나의 파일에서 모든 기능을 처리하는 것보다 코드의 구조를 이해하기 쉽고 유지보수하기 편리합니다.

또한 특정 기능을 수정할 때 다른 영역에 미치는 영향을 줄일 수 있으며, 여러 개발자가 각 계층을 나누어 작업하기에도 유리합니다.
